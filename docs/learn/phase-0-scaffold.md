# Phase 0 - Scaffold: complete code explanation

Version **0.1.0**. This phase writes no computer vision yet. It builds the skeleton every later
phase plugs into: a Python package, a command-line tool, a configuration system, a pipeline
that runs stages in order, the data model that carries results, tests, automatic checks on
GitHub, and a Docker image.

Why start here? A CV project grows into dozens of modules. If every phase invented its own way
of loading files, passing results and reporting errors, Phase 7 (the web app) would have to
glue together eight different styles. Deciding these once, now, means each later phase only
adds a new *stage*.

---

## 1. Big picture

```
            findoc process photo.jpg --out result.json
                              |
                         cli.py (Typer)
                              |
                    pipeline.process(path)
                              |
          +-------------------+--------------------+
          |  Pipeline.run():                       |
          |   1. detect input kind (image/video)   |
          |   2. create a Document                 |
          |   3. for each stage: call it, time it, |
          |      record success or failure         |
          +-------------------+--------------------+
                              |
                Document.result()  ->  JSON file
```

In Phase 0 the only stage is `load` (reads the image). Phase 1 adds `quality`, `detect`,
`rectify` and `ocr`; Phase 4 adds `recon3d`; and so on. The CLI, the JSON format and the error
handling stay the same throughout.

---

## 2. How a run flows, step by step

When you type `findoc process data/samples/cheque.jpg --out outputs/r.json`:

1. **Windows finds `findoc.exe`** in your virtual environment's `Scripts` folder. That file was
   generated by `pip install -e .` from the `[project.scripts]` line in `pyproject.toml`. It
   simply calls `findoc.cli:app`.
2. **Typer parses the arguments** (`cli.py`). It checks that the file exists (`exists=True`)
   and that it's a file, not a folder (`dir_okay=False`). If not, it prints an error and stops.
3. **Settings load** (`config.py`): defaults, overridden by a `.env` file, overridden by
   environment variables starting with `FINDOC_`.
4. **Logging is configured** (`logging.py`) at INFO level, or DEBUG with `--verbose`.
5. **`process()`** (`pipeline.py`) builds the default pipeline and calls `run()`.
6. **`run()`** asks `io.detect_kind()` whether the file is an image or a video (by extension),
   creates a `Document`, then calls each stage in order. Each call is timed and wrapped in
   `try/except`, so one broken stage marks the document `failed` instead of crashing.
7. **The `load` stage** reads the image into a NumPy array (`io.load_image`) and stores it in
   `doc.original`.
8. **Back in the CLI**, a Rich table of stages and timings is printed, then the result is
   converted to JSON (`Document.result()`, which leaves the image arrays out) and written to
   `--out`.
9. **Exit code**: 0 on success, 1 if the status is `failed`. Exit codes let scripts and CI
   detect failure automatically.

## 3. File-by-file walkthrough

### 3.1 `pyproject.toml`: the project's identity card

Modern Python projects describe themselves in one file. Its sections:

| Section | What it does |
| --- | --- |
| `[build-system]` | Which tool turns the source into an installable package. We use **hatchling**. |
| `[project]` | Name, version, description, Python version, licence, authors, keywords. |
| `dependencies` | Libraries always installed: NumPy, OpenCV, Pillow, Pydantic, Typer, Rich. |
| `[project.optional-dependencies]` | "Extras" installed only on request, e.g. `pip install -e ".[dev]"`. `ocr` pulls EasyOCR (heavy, needs PyTorch), `recon3d` pulls pycolmap/Open3D for Phase 4, `dev` pulls pytest/ruff/mypy. Keeping them optional means the core installs fast and CI stays quick. |
| `[project.scripts]` | `findoc = "findoc.cli:app"` creates the `findoc` command. |
| `[tool.hatch.build.targets.wheel]` | Tells hatchling the package lives in the `findoc/` folder. |
| `[tool.ruff]` / `[tool.ruff.lint]` | Linter settings: 100-character lines, and which rule families to enforce (E/F errors, I import order, B likely bugs, UP modern syntax, N naming, SIM simplifications). `B008` is ignored because Typer deliberately uses `typer.Option(...)` calls as default values. |
| `[tool.pytest.ini_options]` | Where tests live and default flags: `--cov=findoc` measures how much code the tests execute. |
| `[tool.mypy]` | Static type checker settings (used from later phases). |

**Why `opencv-python-headless`?** The normal `opencv-python` bundles GUI code (windows,
`cv2.imshow`) that needs display libraries. Servers, Docker and CI have no display, so the
headless build is smaller and avoids missing-library errors. We show images through Streamlit
instead of `imshow`.

**Editable install (`pip install -e .`)**: instead of copying the code into `site-packages`,
pip links to your folder, so edits take effect immediately without reinstalling.

### 3.2 `findoc/__init__.py`: package marker and version

A folder becomes an importable package when it contains `__init__.py`. Ours holds the module
docstring and `__version__ = "0.1.0"`, which the CLI prints. The version here must match
`pyproject.toml`; both are bumped at the end of each phase.

`__all__` lists the public names exported by `from findoc import *`.

### 3.3 `findoc/__main__.py`: `python -m findoc`

Running `python -m findoc ...` executes this file. It just calls the Typer app, so the tool
works even if the `findoc` command isn't on your PATH.

### 3.4 `findoc/config.py`: configuration

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="FINDOC_", env_file=".env", extra="ignore")
    log_level: str = "INFO"
    blur_threshold: float = 100.0
    ...
```

- `BaseSettings` (from **pydantic-settings**) reads each field from, in priority order:
  environment variable `FINDOC_<FIELD>` > `.env` file > the default written in the class.
  So `set FINDOC_BLUR_THRESHOLD=80` (Windows) changes the blur threshold without editing code.
- Each field has a **type**. Pydantic converts and validates: `FINDOC_MAX_SIDE_PX=abc` would
  raise a clear error instead of failing mysteriously later.
- `extra="ignore"` means unknown variables in `.env` are skipped, not errors.
- The fields already reserve values for later phases: `blur_threshold` and `min_coverage`
  (Phase 1 quality gate), `risk_medium` / `risk_high` (Phase 5 risk bands).

```python
@lru_cache
def get_settings() -> Settings:
    return Settings()
```

`@lru_cache` remembers the return value, so settings are read from disk once and every module
gets the same object. This is a simple **singleton** pattern.

`.env.example` documents every variable. Users copy it to `.env`. The real `.env` is in
`.gitignore` because it may later hold secrets (database passwords in Phase 7).

### 3.5 `findoc/logging.py`: readable logs

- `setup_logging(level)` configures Python's built-in `logging` once, with **Rich's** handler
  for coloured, timestamped output and pretty tracebacks.
- The `_CONFIGURED` flag prevents adding duplicate handlers if it's called twice (which would
  print every message twice).
- `get_logger(__name__)` gives each module its own named logger, so log lines show which module
  wrote them.

Why logging and not `print`? Logs have levels (DEBUG/INFO/WARNING/ERROR) you can turn up or
down, and in Phase 7 they can be routed to files or monitoring without touching the code.

### 3.6 `findoc/types.py`: the data model

This is the most important design file. Every stage reads and writes the same `Document`.

**Enums** (`InputKind`, `DocType`, `Status`) restrict a value to a fixed set. `class
Status(str, Enum)` inherits from `str` too, so values serialise to JSON as plain strings
(`"ok"`, `"rejected_quality"`, `"failed"`). Using an enum instead of raw strings means a typo
like `"rejcted"` is caught immediately.

**Pydantic models** (`BaseModel`) are classes with typed fields that are validated on creation
and convert to and from JSON for free:

| Model | Represents | Used from |
| --- | --- | --- |
| `BBox` | A rectangle `(x0, y0, x1, y1)` on the page | Phase 2 (field boxes) |
| `ExtractedField` | One extracted value: name, value, confidence, box | Phase 2 |
| `CheckResult` | One fraud/validation check: fired?, severity, confidence, reason, evidence | Phase 5 |
| `StageLog` | Name, duration in ms, success, note for each stage run | Phase 0 |
| `Document` | Everything known about one input, carried through the pipeline | Phase 0 |

These match the data design in the SRS (section 11) and the risk formula (section 10.6):
`severity` and `confidence` are the `s_i` and `c_i` of the risk score.

Key details in `Document`:

```python
model_config = ConfigDict(arbitrary_types_allowed=True)
original: np.ndarray | None = Field(default=None, exclude=True)
quality: dict[str, float] = Field(default_factory=dict)
```

- Pydantic only knows standard types. `arbitrary_types_allowed=True` lets us store NumPy
  arrays (images).
- `exclude=True` keeps the image arrays out of `model_dump()`, so the JSON result never
  contains megabytes of pixel data.
- `default_factory=dict` gives each document its **own** empty dict. Writing `= {}` directly
  is a classic Python bug: all instances would share one dict.

`result()` returns `self.model_dump(mode="json")`: a plain dictionary where enums become
strings and paths become text, ready for `json.dumps`.

### 3.7 `findoc/io.py`: reading inputs

```python
def detect_kind(path):        # by file extension, raises ValueError if unsupported
def load_image(path):
    data = np.fromfile(str(path), dtype=np.uint8)
    img = cv2.imdecode(data, cv2.IMREAD_COLOR)
```

**Why not just `cv2.imread(path)`?** On Windows, `cv2.imread` fails silently (returns `None`)
for paths with non-ASCII characters, and it's common to have such folder names. Reading the raw
bytes with NumPy and decoding them with `cv2.imdecode` works for any path. `save_image` does the
reverse (`imencode` then `tofile`).

`IMREAD_COLOR` always returns a 3-channel **BGR** image (OpenCV's channel order is
blue-green-red, not RGB; remember this when showing images in Streamlit later).

### 3.8 `findoc/pipeline.py`: the heart of the design

```python
Stage = Callable[[Document], Document]
```

A **stage** is any function that takes a `Document` and returns it. That one-line contract is
the whole extension mechanism: Phase 1 writes `def quality_stage(doc): ...` and adds it to the
list. Nothing else changes.

```python
class Pipeline:
    def __init__(self, stages=None):
        self.stages = stages or [("load", load_stage)]

    def add(self, name, stage):
        self.stages.append((name, stage))
        return self          # allows chaining: Pipeline().add(...).add(...)

    def run(self, source):
        doc = Document(source=source, kind=detect_kind(source))
        for name, stage in self.stages:
            if doc.status is not Status.OK:
                break                      # e.g. quality gate rejected the photo
            t0 = time.perf_counter()
            try:
                doc = stage(doc)
                ok, note = True, ""
            except Exception as exc:
                log.exception(...)         # full traceback in the log
                doc.status = Status.FAILED
                ok, note = False, str(exc)
            doc.stages.append(StageLog(stage=name, ms=..., ok=ok, note=note))
        return doc
```

Design decisions worth explaining in a viva:

- **Early stop**: if a stage sets `status` to anything other than `OK` (for example, Phase 1's
  quality gate sets `REJECTED_QUALITY`), later stages are skipped. No point running OCR on a
  blurry photo.
- **Failure isolation**: an exception inside one stage is recorded, not raised. The result
  still comes back with the stage name and error message, which is what a web API (Phase 7)
  needs to tell the user what went wrong.
- **Timing every stage** with `time.perf_counter()` (a high-resolution clock) gives the
  per-stage latency numbers required by the non-functional requirements (NFR-PER) for free.
- This is the **Pipes and Filters** architectural pattern (related to the Chain of
  Responsibility pattern).

`load_stage` reads the image for image inputs; for videos it only notes that video support
arrives in Phase 3. `process(source)` is the public one-call entry point the CLI, tests and
(later) the API use.

### 3.9 `findoc/cli.py`: the command-line tool

- `typer.Typer(...)` creates the app. `no_args_is_help=True` prints help when you run plain
  `findoc`.
- `@app.command()` turns a normal function into a sub-command. Typer reads the function's
  **type hints** to build the interface: `source: Path` becomes a required argument,
  `out: Path | None = typer.Option(None, "--out", "-o")` becomes an optional flag.
- `process_cmd` runs the pipeline, prints a Rich `Table` of stages, prints status and
  messages, writes JSON if `--out` was given (`encoding="utf-8"` matters on Windows, whose
  default encoding is not UTF-8), and exits with code 1 on failure (`raise typer.Exit(code=1)`).

### 3.10 The stage packages: `preprocess/`, `track/`, `recon3d/`, `classify/`, `localize/`, `recognize/`, `fraud/`, `export/`

Each contains only an `__init__.py` with a docstring stating which phase fills it and which
course outcome it serves. Creating them now fixes the architecture from the SRS (section 13.3)
in the folder structure, so the repo reads like the design document.

### 3.11 `tests/`: automated tests

**`conftest.py`** defines a **fixture**: `sample_image` draws a fake document (a light
quadrilateral "page" with text) on a grey "desk" using OpenCV, saves it in `tmp_path` (a fresh
temporary folder pytest creates per test) and returns the path. Any test that lists
`sample_image` as a parameter receives it automatically. We generate the image instead of
committing a photo so tests never depend on real documents.

**`test_pipeline.py`**:

| Test | Proves |
| --- | --- |
| `test_detect_kind` | Extensions map correctly; `.JPG` works (case-insensitive); unsupported types raise `ValueError` (`pytest.raises`). |
| `test_load_image` | Images load with the right shape `(height, width, 3)`. |
| `test_process_image` | A full run succeeds, the stage list is correct, and image arrays never appear in the JSON. |
| `test_failing_stage_is_recorded` | A stage that raises sets status `failed` and records the error, without crashing. |
| `test_pipeline_stops_after_rejection` | After a stage rejects the document, later stages don't run. |

**`test_cli.py`** uses Typer's `CliRunner`, which runs the CLI inside the test process and
captures its output and exit code, so we test the real command without spawning a shell.

Run with `pytest`. The coverage report lists, per file, which lines no test executed. Phase 0
is at 93%; the requirement (NFR-MNT-02) is at least 75%.

### 3.12 `.github/workflows/ci.yml`: Continuous Integration

GitHub runs this automatically on every push to `main` and every pull request:

- **`lint-and-test`** job, run twice via a **matrix** (Python 3.10 and 3.11): check out code,
  install Python (with pip caching for speed), `pip install -e ".[dev]"`, run `ruff check`
  (lint), `ruff format --check` (formatting), then `pytest`.
- **`docker`** job (`needs: lint-and-test`, so it only runs if tests pass): builds the image
  and runs `findoc version` inside it as a smoke test.

The green badge in the README is this workflow's live status. CI proves the project installs
and passes on a clean machine, not just yours.

### 3.13 `Dockerfile` and `.dockerignore`

```dockerfile
FROM python:3.11-slim                      # small official base image
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
RUN apt-get install ... libglib2.0-0 libgl1    # system libraries OpenCV needs
COPY pyproject.toml README.md ./
COPY findoc ./findoc
RUN pip install .
RUN useradd --create-home appuser && USER appuser   # don't run as root
ENTRYPOINT ["findoc"]
CMD ["--help"]
```

- `PYTHONUNBUFFERED=1` makes logs appear immediately in `docker logs`.
- Running as a non-root user is a basic container security practice.
- `ENTRYPOINT` + `CMD`: `docker run findoc-guard` prints help; `docker run findoc-guard process
  x.jpg` runs `findoc process x.jpg`.
- `.dockerignore` keeps the virtual env, git history, tests, docs and data out of the image,
  making builds faster and the image smaller.

### 3.14 Repository hygiene files

| File | Purpose |
| --- | --- |
| `.gitignore` | Never commit virtual envs, caches, `.env` secrets, datasets, model weights (`*.pt`), 3D outputs (`*.ply`), videos. Large binaries bloat git history permanently, and real documents must never be committed. |
| `.gitattributes` | Normalises line endings to LF in the repo. Windows uses CRLF; without this, every file can look "changed" between Windows and Linux (CI). Marks images and PDFs as binary. |
| `.pre-commit-config.yaml` | Optional hooks that run ruff and basic checks before each commit (`pre-commit install` to enable). Blocks files over 2 MB. |
| `.env.example` | Template documenting every setting. |
| `LICENSE` | MIT: others may reuse the code with attribution. Recruiters expect a licence on public repos. |
| `CHANGELOG.md` | What changed in each version. One minor version per phase ([Semantic Versioning](https://semver.org/)). |
| `data/README.md` | Data policy (synthetic or consented only) and which data folders are tracked. |
| `docs/` | SRS & design PDF, diagrams (PNG) and their Mermaid sources (`docs/diagrams/src/`) so they can be regenerated. |

## 4. Concepts used in this phase

| Concept | One-paragraph explanation |
| --- | --- |
| Virtual environment | An isolated copy of Python with its own packages (`.venv`), so this project's library versions don't clash with other projects. Activate it before working. |
| Type hints | `def f(path: Path) -> Document` documents expected types. Python doesn't enforce them at runtime, but Typer, Pydantic and mypy use them. |
| `from __future__ import annotations` | Makes all type hints lazy strings, enabling modern syntax like `Path \| None` on older Python versions and avoiding import-order problems. |
| Separation of concerns | CLI (interface), pipeline (orchestration), stages (algorithms), types (data) and config live in separate files, so each can change independently. |
| Pipes and Filters | Data flows through a sequence of independent processing steps with a shared interface. |
| Fail-soft error handling | Record errors in the result instead of crashing, so callers always get an explanation. |
| Testing pyramid | Many fast unit tests (functions), fewer integration tests (whole pipeline), few end-to-end tests (CLI, later the UI). |
| CI | Every change is automatically installed and tested on a clean machine. |
| Semantic versioning | MAJOR.MINOR.PATCH. We bump MINOR each phase (0.1 to 0.8) and reach 1.0 at completion. |

## 5. Try it yourself

1. Run `findoc process` on any photo with `--out outputs/test.json` and open the JSON. Find
   the `load` stage's timing.
2. Set `FINDOC_LOG_LEVEL=DEBUG` (`$env:FINDOC_LOG_LEVEL="DEBUG"` in PowerShell) and run again.
   What changed?
3. In a Python shell, build `Pipeline().add("hello", lambda d: (d.messages.append("hi"), d)[1])`
   and run it on an image. Where does `"hi"` appear in the result?
4. Write a test in `tests/test_pipeline.py` that checks a `.webp` file is detected as an
   image. Run `pytest`.
5. Break something on purpose (e.g. make `load_stage` raise an error) and run the CLI. Read
   the stage table and the exit code (`echo $LASTEXITCODE` in PowerShell). Undo the change.

## 6. Viva and interview questions

**Q: Why did you build a pipeline framework before any CV code?**
A: The system has eight stages added over eight phases. A common `Stage` interface and a shared
`Document` model mean each phase plugs in without rewriting earlier code, and the CLI, the API
and the tests all call the same `process()` function.

**Q: What happens if OCR crashes on one document?**
A: `Pipeline.run` catches the exception, sets the status to `failed`, records the stage name and
error message in `stages`, logs the traceback, and returns the document. The caller gets a
structured explanation instead of a crash.

**Q: Why Pydantic instead of plain dictionaries?**
A: Validated, typed fields catch errors early, and `model_dump(mode="json")` gives the JSON
output schema for free. The same models will define the FastAPI request and response schemas
in Phase 7.

**Q: How do you keep images out of the JSON output?**
A: The image fields are declared with `Field(exclude=True)`, so `model_dump` skips them.

**Q: Why `cv2.imdecode(np.fromfile(...))` instead of `cv2.imread`?**
A: `cv2.imread` can't open paths with non-ASCII characters on Windows; reading the bytes with
NumPy and decoding them in memory works for any path.

**Q: How do you make sure the project works on a machine other than yours?**
A: GitHub Actions installs it from scratch on Linux with Python 3.10 and 3.11, runs lint and
tests, builds the Docker image and runs it. The README badge shows the current result.

**Q: How do you configure thresholds without changing code?**
A: Pydantic-settings reads `FINDOC_*` environment variables or a `.env` file, with typed
validation and documented defaults in `.env.example`.

**Q: What is test coverage and what's yours?**
A: The share of code lines executed by the tests: 93% in Phase 0, against a requirement of at
least 75%.
